## 高速バッチ運用（2026-07-10から適用）

- 自治体1件ごとの `npm run build`、Vercel deploy、本番全ページ確認は行わない。
- 調査・データ追加は原則1都道府県単位、最低でも20自治体または新規100制度を1バッチとしてまとめる。
- 20自治体または新規100制度ごとに実行する軽量検証:
  - `npx eslint src/data/grants/verified-local-misc-2026.ts`
  - `git diff --check`
  - 追加URLのGET追従到達確認
  - 重複・必須項目・schema確認
  - `npm run audit:coverage`
- 1都道府県完了時にだけ、上記に加えて上限付きフルbuild、1コミット、Vercel prebuilt deploy、代表ページの本番確認を行う。
- Discoveryは公式ドメインの `sitemap.xml`、サイト内リンク、制度一覧、担当課カテゴリ、PDFリンクから候補URLを一括収集する。
- Verificationでは一覧・検索結果・トップページだけを最終sourceにせず、個別ページまたは公式PDFで確認できた制度のみ掲載する。
- 公式URLが404、本文に制度名がない、金額/上限や対象が確認できないものは候補台帳に残し、掲載しない。
- 外部待機で作業を止めない。Vercel prebuilt deployが長時間 `Deploying outputs...` の場合はdeployment IDと最終ログを記録し、30〜60分ごとのinspectだけにする。

### 高速化実測と採用手順（2026-07-11追記）

- 直近17自治体の実績は平均約10分09秒、約5.9自治体/時。黒松内町は約12分36秒、ツール出力53回、巨大HTML/PDF出力によるcontext compaction復旧だけで約2分23秒（約19%）を消費。
- 会話へHTML/PDF本文を大量出力しない。公式HTML/PDFはローカルファイルまたはJSONへ保存し、会話には制度名・対象・金額/上限・期限/受付状況・公式URL・短い根拠だけを出す。
- `scripts/validate-official-candidate-urls.mjs` は `.cache/official-discovery` の24時間以内の成功キャッシュを再利用する。蘭越町代表サンプルでは99URL validationがキャッシュ利用99件・再取得0件で0.04秒、再取得相当では84URLで0.19秒。
- `scripts/discover-official-candidates.mjs` は `src` 由来の画像・JS・CSS等assetを除外し、`href` とsitemap上のページ/PDF/DOC/XLS系だけを探索する。一次探索100URLで候補が弱い場合のみ300URLまで深掘りし、低優先候補は削除せず第2巡へ残す。
- 蘭越町代表サンプルでは、Discoveryはキャッシュ利用時0.13秒、300URL探索、候補99件。強候補をtitle/h1/PDF強語だけに絞ると0件になったため、現時点では強候補だけに依存せず、スコア上位とカテゴリ導線をVerificationで確認する。
- 品質ガード: 今金町はデータ上29件、チェックリストが28件だったため本追記で29件へ補正。`localVerifiedGrant` の `verifiedAt/publishedAt` は固定値ではなく、`sourceNote` 内の `YYYY年M月D日` から反映するよう修正済み。HTTP 200だけで本文一致済みとは扱わず、最終採用は個別公式本文/PDFで制度名・対象・金額/上限・条件・期限/受付状況を確認する。

### 第2段高速化ルール（礼文町完了後から適用）

- 1ハートビート1自治体で終了しない。原則として1ターンで自治体コード順に3〜5自治体、又は新規60〜100制度、又は実働45〜55分の最初に達するまで連続処理する。
- 重い自治体、150件超のshortlist、公式サイト障害、PDF抽出不良がある場合は、候補・保留理由・次地点をcheckpointへ残し、品質条件が満たせる候補だけ採用して次自治体へ進む。
- 自治体ごとの作業は、公式本文/PDFの必須項目確認、slug/schema、変更URL到達、自治体別checkpoint保存に限定する。`npx eslint`、`git diff --check`、`npm run audit:coverage`、チェックリスト集計、Git commitは原則3〜5自治体又は60〜100制度ごとに1回へ集約する。
- 同じ監査を連続2回実行しない。助成金データ本体とこのチェックリスト以外の既存変更はstageしない。
- shortlist再スコアリングでは、title/h1/main/article/URLの制度強語に加え、金額表現（円・万円・上限・月額・年額・補助率・1/2等）、対象表現（対象者・要件・世帯・事業者等）、期限/受付表現（申請・募集・受付・締切・令和8年度等）が同一ページにある個別ページ/PDFを最優先にする。
- トップ、カテゴリ、サイトマップ、共通ナビ一致のみの候補は低優先度へ落とす。ただし低優先候補は削除せず第2巡台帳へ残す。
- shortlistが150件超又はcrawl候補の40%超の場合、本文スニペットをローカルJSON/CSVへ抽出して再選別し、会話へ大量HTML/PDFを出さない。
- context compaction対策として、各自治体完了時に自治体コード、採用/保留/除外件数、取得済みファイル、次地点を小さい進捗JSONへ保存する。compact後はそのJSON、HEAD、対象2ファイルだけを読み、グローバル探索や既読資料の再読をしない。
- 次の15自治体で、自治体/時、制度/時、1自治体あたりのturn/compaction数、shortlist→採用率、監査回数、commit数を測る。基準値は全体5.4自治体/時・直近約5.0自治体/時、第一目標は品質維持のまま6.5自治体/時以上。悪化した施策は戻す。
