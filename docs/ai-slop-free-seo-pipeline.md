# AI臭除去SEO記事パイプライン

作成日：2026年7月19日
対象：支援制度ナビ
参照：[The steps my SEO pipeline runs before it publishes](https://x.com/maks6361/status/2076589639553397155)

## 採用した考え方

参照した投稿は、キーワード選定から公開までを七つの工程に分け、各工程に停止条件を置いています。

支援制度ナビでは、流暢な文章より公式情報との一致を先に検査します。
品質スコアが基準を超えても、自動公開はしません。
記事候補は`draft`かつ`noindex`で止まり、人手確認後の画像作成、ビルド、本番反映は別の作業として扱います。

このパイプラインは既存の`audit:content`を置き換えません。
既存監査は公開中の制度データを検査し、このパイプラインは公開前の記事候補だけを検査します。

## 七つの工程

### 1．キーワードバックログ

`data/seo-articles/keyword-backlog.json`の`pending`項目だけを処理します。
優先度が同じ場合は記録順を保ちます。

対象がなければ`EMPTY_KEYWORD_BACKLOG`で停止します。
似た語句を推測して記事を作る処理はありません。

### 2．検索意図

キーワードから次の意図を分類します。

- 比較
- 申請方法
- 用語の意味
- 選び方
- 問題解決
- 一覧
- 対象条件
- 申請期限
- 支援額
- 一般的な情報確認

記事本文と見出しに、その意図へ答える語句があるかを品質採点で再確認します。

### 3．公式根拠

`data/seo-articles/truth-packets.json`には、記事より先に確認した事実を保存します。

一つの公式出典には、ページ名、URL、確認日、照合方法、実施機関との一致、制度名との一致を記録します。
HTTP応答だけでは公式根拠として扱いません。

事実は`exists`か`doesNotExist`に分けます。
たとえば、公式資料に必要書類の記載が見つからなかった場合は`doesNotExist`です。
記事側がその項目を「記載あり」と主張すると、`FACT_ASSERTION_MISMATCH`で停止します。

人手確認の表示には`verificationMethod`が`human`または`mixed`であり、`humanReviewedAt`に実際の確認日があることを要求します。
自動照合だけの資料を人手確認済みへ変更する処理はありません。

### 4．記事構造

ドラフトJSONには次の項目が必要です。

| 項目 | 用途 |
|---|---|
| `keywordId` | バックログと公式根拠の対応 |
| `slug` | 記事候補のURL識別子 |
| `title` | キーワードを含む簡潔な題名 |
| `metaDescription` | 検索結果向け説明 |
| `shortAnswer` | 冒頭の短い回答 |
| `aiAnswer` | AI検索にも解釈しやすい、根拠付きの要約 |
| `sections` | 制度固有の本文 |
| `faq` | 本文にも表示する質問と回答 |
| `internalLinks` | 関連制度、地域、目的、申請ガイドへのリンク |
| `cta` | 検証済み公式URLへの確認導線 |
| `claims` | 本文の主張と事実IDの対応 |
| `revisionCycle` | 自動修正の実行回数 |

本文に出典がない条件、書類、申請方法、採択可能性を補いません。
公式資料で確認できない項目は、確認できないと明示するか、節ごと省きます。

### 5．AI臭の二段階検査

一回目は、意味を歪めやすい表現を検出します。

- 受給や採択の断定
- 誇張語
- 具体性のない企業語
- 作為的な問いかけ
- 空虚な宣伝文
- 根拠のない採択率、満足度、監修表示

二回目は、文章の組み立てを検出します。

- 320文字を超える段落
- 同じ書き出しの反復
- 同じ語尾の過度な反復
- 同じ接続語の連打
- 不自然なダッシュや省略記号

検査は文章を勝手に書き換えません。
見つかった項目を修正理由として返し、構成工程へ戻します。

### 6．品質採点と修正

標準の合格点は85点です。

| 評価軸 | 配点 |
|---|---:|
| 公式根拠との一致 | 30 |
| 日本語の読みやすさ | 20 |
| 検索意図との一致 | 15 |
| 必須構造 | 15 |
| 主張の出典網羅 | 15 |
| 題名と説明文 | 5 |

公式根拠、必須構造、AI臭検査のどれかに失敗した場合は、合計点にかかわらず不合格です。
不合格の記事は`nextStage: structure`として戻します。

自動修正は標準で三回までです。
`revisionCycle`が上限に達すると`blockedRevisionLimit`になり、人手確認へ送ります。
回数を増やして根拠不足を押し切ることはできません。

### 7．公開前の停止

合格時の状態は次のとおりです。

- `status: reviewReady`
- `contentStatus: draft`
- `indexStatus: noindex`
- `requiresHumanApproval: true`
- 画像作成：保留
- ビルド：未実行
- 本番デプロイ：禁止
- 通知：コンソールと監査レポート

実行結果は`reports/seo-article-pipeline/latest.json`と`latest.md`に保存します。
レポートは作業用であり、公開画面やサイトマップから参照しません。

## データの追加手順

1. Search Consoleなどの実測値からキーワード候補を選び、バックログへ追加する。
2. 制度の実施機関が公開したページを読み、公式根拠パケットを作る。
3. `exists`と`doesNotExist`を分け、記事に使う主張を事実IDへ紐付ける。
4. `data/seo-articles/drafts/`へドラフトJSONを置く。
5. `npm run seo:article`を実行する。
6. 修正理由があればドラフトを直し、`revisionCycle`を更新する。
7. `reviewReady`になった記事を人が公式資料と照合する。

実在するキーワード、公式根拠、記事ドラフトがまだないため、初期バックログは空です。
この状態でコマンドを実行すると、近い話題を作らず正常停止します。

## コマンド

```bash
# 優先度が最も高いpending記事を検査
npm run seo:article

# pending記事をすべて検査。要修正や根拠不足があれば終了コード1
npm run audit:seo-articles

# パイプラインの単体テストを含む全単体テスト
npm test
```

`audit:seo-articles`が成功しても、本番公開の承認にはなりません。
人手確認後の公開手順では、既存の`check:copy`、`audit:content`、`audit:build`、`audit:links`も通す必要があります。
